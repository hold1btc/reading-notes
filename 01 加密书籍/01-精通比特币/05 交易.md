## 本章节的主旨

承接前两章，本章继续讲解比特币的所有权如何转移。通过逐字段拆解交易序列化格式，我们看到交易数据从传统的“版本号 + 输入 + 输出 + 锁定时间”结构，演进为包含 Marker、Flag 和见证数据的扩展序列化格式。这一变化将见证数据从 txid 计算中隔离出去，解决了传统格式下的循环依赖、第三方篡改和第二方篡改等问题。本章最后还介绍了 Coinbase 这一特殊交易的字段组成及其特殊规则。

## 本章节大纲

交易序列化（传统/扩展） ➡️ 版本号 ➡️ Marker和Flag ➡️ 交易输入（数量+pointout, scriptsig， nSequence） ➡️ 交易输出（数量+金额, scriptPublickey） ➡️ 见证结构 ➡️ 锁定时间 ➡️ coinbase的交易序列化

## 关键定义

1. 比特币交易的扩展序列化结构：序列化数据用于网络传输、区块存储和交易承诺；全节点收到后先解析，再按共识规则和策略进行验证。

```text
版本号
→ [Marker + Flag]       仅当交易包含 witness 时存在
→ 输入数量
→ 每个输入
→ 输出数量
→ 每个输出
→ [witness 数据]        仅当交易包含 witness 时存在
→ 锁定时间
```

2. 版本：前四个字节是版本号。比特币交易的最初版本是版本 1（0x01000000）。BIP68 软分叉引入了相对时间锁，其额外约束仅适用于版本2及以上的交易，版本1不受影响。

3. 扩展Marker和Flag字段：用“无效的输入数量”作为格式切换信号，既让新节点识别扩展格式，又让旧节点自然拒绝。新节点剥离 witness 和 Marker/Flag 后再中继给旧节点.

4. 交易输入部分：包含输入数量（CompactSize） + 每个输入（outpoint、scriptSig、sequence）。SegWit 的 witness 数据不在输入结构里，而是在交易末尾单独序列化。

5. 交易输出部分：输出数量（CompactSize） + 每个输出（金额、scriptPubKey）。其中 scriptPubKey是带 CompactSize 长度前缀的锁定脚本，规定这笔钱以后怎么花。
   
6. 见证隔离：是 SegWit 引入的新字段，用来存放原本放在 scriptSig 里的解锁数据，如签名、公钥、脚本、哈希原像等。它的核心作用是：把见证数据从 txid 计算中隔离出去，从而解决循环依赖、第三方篡改和第二方篡改。

7. 锁定时间：用来表示这笔交易最早何时可以被包含进区块。早期它只是矿工的政策，后来通过软分叉变成了共识规则。

8. Coinbase交易的数据结构

```text
输入：
  1 个输入，全零 txid + 0xffffffff，coinbase 字段含区块高度等数据

输出：
  输出 0：OP_RETURN witness commitment（因为区块有 SegWit 交易）
  输出 1：矿工收款地址（补贴 + 手续费）
  可能还有输出 2、3...：矿工拆分奖励到多个地址
```

9. Coinbase与普通交易的对比

| 对比项 | 普通交易 | Coinbase 交易 |
| :--- | :--- | :--- |
| **输入数量** | 至少 1 个，可多个 | 只能 1 个 |
| **输入引用** | 引用之前某个 UTXO | txid 全零 + 输出索引 `0xffffffff` |
| **输入脚本字段名** | `scriptSig` | `coinbase` 字段 |
| **输入脚本长度** | 可变 | 2 到 100 字节 |
| **输入脚本是否执行** | 是 | 否 |
| **输出总额限制** | 不能超过输入总额 | 不能超过费用 + 补贴 |
| **输出成熟规则** | 无 | 100 次确认后才能花 |
| **SegWit 承诺** | 无 | 有 SegWit 交易时必须包含 |
| **创建者** | 任何用户 | 矿工 |

10. 权重和V字节

| 字段 | 因子 | Alice 的交易权重 |
| :--- | :---: | :--- |
| **Version（版本号）** | 4 | 16（版本号占 4 字节，乘以 4 后为 16；16 权重 = 4 vbytes） |
| **Marker & Flag（标记与标志）** | 1 | 2 |
| **Inputs Count（输入数量）** | 4 | 4 |
| **Outpoint（输出点）** | 4 | 144 |
| **Input script（输入脚本）** | 4 | 14 |
| **Sequence（序列号）** | 4 | 16 |
| **Output script（输出脚本）** | 4 | 4 |
| **Amount（金额）** | 4 | 64（2 个输出） |
| **Output script（输出脚本）** | 4 | 232（2 个输出，脚本不同） |
| **Witness Count（见证项数量）** | 1 | 1 |

## 疑问及解答

1. 新/旧节点如何解析 segwit 扩展/传统序列化交易的数据?

```text
新节点：靠第一个字节区分两种格式，流程大致是：

读版本号（4 字节）
        │
        ▼
读下一个字节
        │
        ├── 是 0x00 → 扩展格式
        │     读 Flag
        │     读输入数量
        │     读输入
        │     读输出数量
        │     读输出
        │     读 witness
        │     读锁定时间
        │
        └── 不是 0x00 → 传统格式
              这个字节就是输入数量（CompactSize）
              读输入
              读输出数量
              读输出
              读锁定时间

旧节点：正常 P2P 中继时，新节点通过 NODE_WITNESS 能力协商识别旧节点，主动剥离 witness 和 Marker/Flag，只发传统格式。
旧节点收到后按传统规则解析、验证、转发。如果旧节点直接收到完整扩展格式，它会把 Marker 误读为输入数量 0，判定交易无效并拒绝。

```

2. 交易输入解析流程

```text
输入数量（CompactSize）
  ├── 输入 0
  │     ├── outpoint
  │     ├── scriptSig
  │     └── sequence
  ├── 输入 1
  │     ├── outpoint
  │     ├── scriptSig
  │     └── sequence
  └── ...
```

3. 什么是“带长度前缀的输入脚本字段”

scriptSig 前面先用 CompactSize 写一个长度值，告诉解析器脚本有多少字节，然后才是脚本内容。空脚本的长度前缀是 0x00，非空脚本的长度前缀是对应字节数。解析器靠它知道脚本在哪里结束、sequence 从哪里开始。

4. 一个 32 位 sequence 字段的总结（BIP68定义，开启版本2）

```text
bit 31         bit 22              bit 15 ... bit 0
  │              │                      │
  │              │                      └── 锁定值（16 位）
  │              └── 类型标志：0=区块，1=秒
  └── 禁用标志：0=启用相对时间锁，1=禁用（0xffffffff）
```

5. 交易输出解析流程

```text
输出数量（CompactSize）
  ├── 输出 0
  │     ├── 金额（8 字节）
  │     └── scriptPubKey（带长度前缀：指示脚本长度）
  ├── 输出 1
  │     ├── 金额（8 字节）
  │     └── scriptPubKey（带长度前缀）
  └── ...
```

6. 常见交易输出脚本类型（scriptPubKey 的常见模式）

| 阶段 | 类型 | 关键脚本结构 | 主要特征 | 状态与用途 |
| :--- | :--- | :--- | :--- | :--- |
| **第一阶段：早期与遗留类型** | **P2PK** | `<公钥> OP_CHECKSIG` | 直接暴露公钥，最古老形式 | **已弃用**，仅存于历史 UTXO 中 |
| **第一阶段：早期与遗留类型** | **P2PKH** | `OP_DUP OP_HASH160 <公钥哈希> OP_EQUALVERIFY OP_CHECKSIG` | 公钥哈希，经典 `1` 地址 | **活跃**，历史存量巨大 |
| **第一阶段：早期与遗留类型** | **P2MS** | `<m> <公钥1> ... <公钥n> <n> OP_CHECKMULTISIG` | 原生多签，公钥直接上链 | **遗留**，功能被 P2SH/P2WSH 取代 |
| **第二阶段：脚本哈希时代** | **P2SH** | `OP_HASH160 <赎回脚本哈希> OP_EQUAL` | 脚本哈希，`3` 地址，支持多签和嵌套 SegWit | **活跃**，广泛用于复杂脚本 |
| **第三阶段：SegWit 与 Taproot 时代** | **P2WPKH** | `OP_0 <20字节公钥哈希>` | SegWit v0，P2PKH 的原生 SegWit 版 | **活跃**，主流类型 |
| **第三阶段：SegWit 与 Taproot 时代** | **P2WSH** | `OP_0 <32字节脚本哈希>` | SegWit v0，P2SH 的原生 SegWit 版 | **活跃**，用于复杂脚本 |
| **第三阶段：SegWit 与 Taproot 时代** | **P2TR** | `OP_1 <32字节x-only公钥>` | SegWit v1 / Taproot，Schnorr 签名，隐私与效率最优 | **活跃**，最新标准 |
| **第三阶段：SegWit 与 Taproot 时代** | **OP_RETURN** | `OP_RETURN <数据>` | 不可花费，数据载体，不进入 UTXO 集 | **活跃**，用于数据锚定 |
| **第三阶段：SegWit 与 Taproot 时代** | **非标准脚本** | 任意不符合标准模板的脚本 | 共识允许，但策略通常不中继 | **边缘**，难以传播 |

7. 交易输出没有大小限制，只受交易和区块大小间接约束；但花费时，共识规则要求前序输出的脚本不能超过 10,000 字节。为什么仅在下次花费该输出时才限制，既然为了防止utxo集膨胀，在输出时就应该限制啊？难道是交易输出不用进uxto集？

```text
交易输出确实会进入UTXO集，但“超过10,000字节”这个限制，恰恰是决定它“能不能”进入UTXO集的门槛。
不在UTXO集”且“不可花费”的输出主要有两类：OP_RETURN输出和超大脚本输出。
```

8. 见证结构的解析时，与交易输入数量和顺序一一对应

```text
见证结构：
  输入 0 的见证堆栈：
    <项数 CompactSize>
      <项 0 长度 CompactSize> <项 0 数据>
      <项 1 长度 CompactSize> <项 1 数据>
      ...
  输入 1 的见证堆栈：
    <项数 CompactSize>
      ...
```

9. nLocktime 的3种情况

| locktime 值 | 解释 | 交易何时可被包含 |
| :--- | :--- | :--- |
| `0` | 无限制 | 任何区块 |
| `1` 到 `499,999,999` | 区块高度 | 高度 ≥ locktime 的区块 |
| `≥ 500,000,000` | Unix 时间戳 | MTP > locktime 的区块 |

10. nLocktime 和 sequence 里面的锁定时间有什么区别？

```text
locktime 是“绝对时间锁”，作用在整笔交易上；sequence 里的时间锁是“相对时间锁”，作用在单个输入上。
如果一笔交易的所有输入的 sequence 都设为最大值即 0xffffffff，那么 locktime 被禁用。
这也是为什么很多普通交易的 sequence 设为 0xffffffff：它们不需要 locktime，也不需要 RBF，直接立即有效。
```
11. nLocktime 和 CTLV 为什么必须配合使用？

```text
nLockTime 是标尺：它是交易层面的一个绝对时间参照系，提供了一个具体的数值（区块高度或时间戳）。没有这把标尺，时间锁就失去了比较的对象。
CLTV 是操作码：它是脚本层面的执行指令，负责去读取这把“标尺”上的刻度，并强制要求它达标。
```

12. 交易合法性验证流程

```text
交易输入包含 outpoint
        │
        ▼
全节点用 txid 找到之前交易
        │
        ▼
用输出索引找到特定输出
        │
        ▼
检查该输出是否在 UTXO 数据库中
        │
        ├── 不在 → 无效（不存在或已花费）
        │
        ▼
在 → 获取金额、锁定脚本、确认信息
        │
        ▼
执行脚本，验证签名和条件
        │
        ▼
检查金额是否足够、是否双花
        │
        ▼
验证通过 → 接受交易 → 中继交易
```

## 本章节评价

本章内容密度非常大，很多概念都是学习比特币的基础。我本章最大的收获是搞清楚了几个重点问题：第一，交易在网络传输和区块中是以序列化形式存在的；第二，从传统序列化到扩展序列化是经过 SegWit 升级，目的是解决循环依赖、第三方篡改和第二方篡改等问题；第三，新节点和旧节点如何识别、解析传统格式和扩展格式；第四，交易中每个字段包含的具体内容，以及这些设计背后的原因。总的来说，这章扫清了很多交易数据中的盲区，让我对比特币所有权如何从一方转移到另一方有了更清晰的了解。

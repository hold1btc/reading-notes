## 关键定义

1. 比特币交易的扩展序列化结构：序列化数据用于网络传输、区块存储和交易承诺；全节点收到后先解析，再按共识规则和策略进行验证。

```text
版本号
→ [Marker + Flag]       仅当交易包含 witness 时存在
→ 输入数量
→ 每个输入
→ 输出数量
→ 每个输出
→ [witness 数据]        仅当交易包含 witness 时存在
→ 锁定时间
```
2. 版本：前四个字节是版本号。比特币交易的最初版本是版本 1（0x01000000）。BIP68 软分叉引入了相对时间锁，其额外约束仅适用于版本2及以上的交易，版本1不受影响。

3. 扩展Marker和Flag字段：用“无效的输入数量”作为格式切换信号，既让新节点识别扩展格式，又让旧节点自然拒绝。新节点剥离 witness 和 Marker/Flag 后再中继给旧节点.

5. 交易输入部分：包含输入数量（CompactSize） + 每个输入（outpoint、scriptSig、sequence）。SegWit 的 witness 数据不在输入结构里，而是在交易末尾单独序列化。

6. 交易输出部分：输出数量（CompactSize） + 每个输出（金额、scriptPubKey）。其中 scriptPubKey是带 CompactSize 长度前缀的锁定脚本，规定这笔钱以后怎么花。

7. 常见交易输出脚本类型（ scriptPubKey 的常见模式）

| 阶段 | 类型 | 关键脚本结构 | 主要特征 | 状态与用途 |
| :--- | :--- | :--- | :--- | :--- |
| **第一阶段：早期与遗留类型** | **P2PK** | `<公钥> OP_CHECKSIG` | 直接暴露公钥，最古老形式 | **已弃用**，仅存于历史 UTXO 中 |
| **第一阶段：早期与遗留类型** | **P2PKH** | `OP_DUP OP_HASH160 <公钥哈希> OP_EQUALVERIFY OP_CHECKSIG` | 公钥哈希，经典 `1` 地址 | **活跃**，历史存量巨大 |
| **第一阶段：早期与遗留类型** | **P2MS** | `<m> <公钥1> ... <公钥n> <n> OP_CHECKMULTISIG` | 原生多签，公钥直接上链 | **遗留**，功能被 P2SH/P2WSH 取代 |
| **第二阶段：脚本哈希时代** | **P2SH** | `OP_HASH160 <赎回脚本哈希> OP_EQUAL` | 脚本哈希，`3` 地址，支持多签和嵌套 SegWit | **活跃**，广泛用于复杂脚本 |
| **第三阶段：SegWit 与 Taproot 时代** | **P2WPKH** | `OP_0 <20字节公钥哈希>` | SegWit v0，P2PKH 的原生 SegWit 版 | **活跃**，主流类型 |
| **第三阶段：SegWit 与 Taproot 时代** | **P2WSH** | `OP_0 <32字节脚本哈希>` | SegWit v0，P2SH 的原生 SegWit 版 | **活跃**，用于复杂脚本 |
| **第三阶段：SegWit 与 Taproot 时代** | **P2TR** | `OP_1 <32字节x-only公钥>` | SegWit v1 / Taproot，Schnorr 签名，隐私与效率最优 | **活跃**，最新标准 |
| **第三阶段：SegWit 与 Taproot 时代** | **OP_RETURN** | `OP_RETURN <数据>` | 不可花费，数据载体，不进入 UTXO 集 | **活跃**，用于数据锚定 |
| **第三阶段：SegWit 与 Taproot 时代** | **非标准脚本** | 任意不符合标准模板的脚本 | 共识允许，但策略通常不中继 | **边缘**，难以传播 |
   
## 疑问及解答

1. 新节点为什么可以解析出传统序列化交易的数据?

```text
靠第一个字节区分两种格式，新节点解析交易时，流程大致是：

读版本号（4 字节）
        │
        ▼
读下一个字节
        │
        ├── 是 0x00 → 扩展格式
        │     读 Flag
        │     读输入数量
        │     读输入
        │     读输出数量
        │     读输出
        │     读 witness
        │     读锁定时间
        │
        └── 不是 0x00 → 传统格式
              这个字节就是输入数量（CompactSize）
              读输入
              读输出数量
              读输出
              读锁定时间
```

2. 交易输入解析流程

```text
输入数量（CompactSize）
  ├── 输入 0
  │     ├── outpoint
  │     ├── scriptSig
  │     └── sequence
  ├── 输入 1
  │     ├── outpoint
  │     ├── scriptSig
  │     └── sequence
  └── ...
```

3. 交易输出解析流程

```text
输出数量（CompactSize）
  ├── 输出 0
  │     ├── 金额（8 字节）
  │     └── scriptPubKey（带长度前缀：指示脚本长度）
  ├── 输出 1
  │     ├── 金额（8 字节）
  │     └── scriptPubKey（带长度前缀）
  └── ...
```

4. 交易合法性验证流程

```text
交易输入包含 outpoint
        │
        ▼
全节点用 txid 找到之前交易
        │
        ▼
用输出索引找到特定输出
        │
        ▼
检查该输出是否在 UTXO 数据库中
        │
        ├── 不在 → 无效（不存在或已花费）
        │
        ▼
在 → 获取金额、锁定脚本、确认信息
        │
        ▼
执行脚本，验证签名和条件
        │
        ▼
检查金额是否足够、是否双花
        │
        ▼
验证通过 → 接受交易 → 中继交易
```

5. 什么是“带长度前缀的输入脚本字段”

   scriptSig 前面先用 CompactSize 写一个长度值，告诉解析器脚本有多少字节，然后才是脚本内容。空脚本的长度前缀是 0x00，非空脚本的长度前缀是对应字节数。解析器靠它知道脚本在哪里结束、sequence 从哪里开始。

6. 一个 32 位 sequence 字段的总结（BIP68定义）

```text
bit 31         bit 22              bit 15 ... bit 0
  │              │                      │
  │              │                      └── 锁定值（16 位）
  │              └── 类型标志：0=区块，1=秒
  └── 禁用标志：0=启用相对时间锁，1=禁用（0xffffffff）
```

7. 最后解析的锁定时间和 sequence 里面的锁定时间有什么区别？
```text
locktime 是“绝对时间锁”，作用在整笔交易上；sequence 里的时间锁是“相对时间锁”，作用在单个输入上。
如果一笔交易的所有输入的 sequence 都设为最大值即 0xffffffff，那么 locktime 被禁用。
这也是为什么很多普通交易的 sequence 设为 0xffffffff：它们不需要 locktime，也不需要 RBF，直接立即有效。
```

8. 交易输出没有大小限制，只受交易和区块大小间接约束；但花费时，共识规则要求前序输出的脚本不能超过 10,000 字节。为什么仅在下次花费该输出时才限制，既然为了防止utxo集膨胀，在输出时就应该限制啊？难道是交易输出不用进uxto集？

```text
交易输出确实会进入UTXO集，但“超过10,000字节”这个限制，恰恰是决定它“能不能”进入UTXO集的门槛。
不在UTXO集”且“不可花费”的输出主要有两类：OP_RETURN输出和超大脚本输出。
```

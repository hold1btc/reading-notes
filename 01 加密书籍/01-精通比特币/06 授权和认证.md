## 本章节的主旨

本章主要介绍了交易的授权和认证（上锁和解锁过程，即交易输出和交易输入的构造）。为了满足更多支付场景和对更灵活的支付逻辑的要求，交易输出和输入的构成从最初的P2PK最简单支付场景，到通过脚本哈希隐藏复杂逻辑的P2SH，让多签等复杂脚本得以大规模普及；为了进一步解决交易延展性、区块容量瓶颈问题，隔离见证应运而生，它作为通用的结构性升级，将公钥、签名等解锁见证数据从交易输入中剥离，放到独立的见证结构中，在提升脚本灵活性的同时，彻底解决了比特币的交易延展性问题；而Taproot升级后，依托Schnorr签名和MAST默克尔树，比特币网络可以支持更多隐私性更强、体积更精简的自定义支付逻辑。

## 本章节大纲

### 第一层：授权与认证的“三阶段演进”

- 白皮书阶段：授权 = 公钥，认证 = 签名。

- 传统脚本阶段：授权 = 输出脚本（scriptPubKey），认证 = 输入脚本（scriptSig）。这引入了 P2PK、P2PKH、P2SH、多签、时间锁等丰富形式。

- SegWit 阶段：授权 = 见证程序（Witness Program），认证 = 见证结构（Witness Structure）。认证数据从 scriptSig 剥离，解决了 txid 可篡改性问题。

- Taproot 阶段（进阶）：授权 = 调整后公钥/MAST 承诺，认证 = Schnorr 签名/脚本路径数据。隐私和效率达到新高度。

### 第二层：验证过程的“物理执行”

光知道结构不行，本章还深入了底层执行机制。重点在于理解：

- 栈式执行：脚本是按“后进先出”的规则在栈上操作的。

- P2SH 的“两步验证”：先验证赎回脚本的哈希，再执行赎回脚本本身。这解释了 scriptSig 中“数据在前、脚本在后”顺序的根本原因。

- 标准脚本的验证逻辑：比如 P2PKH 的 OP_DUP OP_HASH160 OP_EQUALVERIFY OP_CHECKSIG 是如何一步步从栈上取数据、比对哈希、验证签名的。

### 第三层：授权条件的“组合与扩展”

本章的重点不仅是“单签”，更是如何用脚本拼出复杂的条件：

- 多签（Multisig）：m-of-n 的授权规则。

- 时间锁：CLTV（绝对时间锁）和 CSV（相对时间锁）如何与脚本结合。

- 哈希锁：HTLC 等条件支付的基础。

- 组合逻辑：用 IF/ELSE 实现“要么满足条件 A，要么满足条件 B”。

## 关键定义

1. 授权

       定义【花费权限归属】的过程就是授权。本质上是将BTC锁在一个脚本中。

2. 认证

       全网【统一验证身份合法性】的过程就叫认证。本质是给这笔BTC解锁的过程。
       比特币的传统交易验证引擎依赖于两部分脚本来验证交易：输出脚本和输入脚本。输出脚本其实就是在做授权，输入脚本在做认证。

3. 脚本类型汇总

| 类型 | 授权：锁定脚本 / 见证程序 | 认证：解锁数据 | 地址前缀 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| **P2PK** | `<公钥> OP_CHECKSIG` | `<签名>` | 无经典地址 | 最早期形式，直接支付到公钥；已不推荐使用 |
| **P2PKH** | `OP_DUP OP_HASH160 <公钥哈希> OP_EQUALVERIFY OP_CHECKSIG` | `scriptSig: <签名> <公钥>` | `1...` | 最经典的传统单签形式 |
| **P2MS** | `<m> <公钥1> ... <公钥n> <n> OP_CHECKMULTISIG` | `scriptSig: <空占位> <签名...>` | 无经典地址 | 原生多签；公钥直接上链，功能多被 P2SH/P2WSH 取代 |
| **P2SH** | `OP_HASH160 <赎回脚本哈希> OP_EQUAL` | `scriptSig: <script_data> <serialized_redeem_script>` | `3...` | 链上只存脚本哈希；支持多签、时间锁、嵌套 SegWit |
| **P2WPKH** | `OP_0 <20字节公钥哈希>` | `scriptSig: 空`；`witness: <签名> <公钥>` | `bc1q...` | 原生 SegWit v0 单签；scriptSig 必须为空 |
| **P2WSH** | `OP_0 <32字节见证脚本哈希>` | `scriptSig: 空`；`witness: <输入栈...> <WitnessScript>` | `bc1q...` | 原生 SegWit v0 复杂脚本；最后一项是见证脚本 |
| **P2SH-P2WPKH** | 外层 P2SH：`OP_HASH160 <redeemScript哈希> OP_EQUAL`；redeemScript 为 `OP_0 <20字节公钥哈希>` | `scriptSig: <redeemScript>`；`witness: <签名> <公钥>` | `3...` | 嵌套 SegWit 单签；兼容旧钱包 |
| **P2SH-P2WSH** | 外层 P2SH：`OP_HASH160 <redeemScript哈希> OP_EQUAL`；redeemScript 为 `OP_0 <32字节见证脚本哈希>` | `scriptSig: <redeemScript>`；`witness: <输入栈...> <WitnessScript>` | `3...` | 嵌套 SegWit 复杂脚本 |
| **P2TR 密钥路径** | `OP_1 <32字节x-only调整后公钥>` | `scriptSig: 空`；`witness: <Schnorr签名>` | `bc1p...` | Taproot 最常见花费方式；链上看起来像普通单签 |
| **P2TR 脚本路径** | `OP_1 <32字节x-only调整后公钥>` | `scriptSig: 空`；`witness: <脚本输入栈...> <脚本> <控制块> [annex]` | `bc1p...` | Taproot 脚本路径；控制块证明脚本被承诺在 MAST 中 |
| **OP_RETURN** | `OP_RETURN <数据>` | 不可花费 | 无 | 数据载体输出；不进入 UTXO 集，不是支付授权 |
| **时间锁组合** | 例如 `CLTV`：`<时间> OP_CHECKLOCKTIMEVERIFY OP_DROP <公钥> OP_CHECKSIG`；`CSV`：`<延迟> OP_CHECKSEQUENCEVERIFY OP_DROP <公钥> OP_CHECKSIG` | 满足时间条件的签名，且交易 `nLockTime`/`nSequence` 匹配 | 取决于外层类型 | 可与 P2SH/P2WSH/P2TR 组合 |
| **哈希锁组合** | 例如 `OP_HASH160 <哈希> OP_EQUALVERIFY <公钥> OP_CHECKSIG` | `<原像> <签名>` | 取决于外层类型 | HTLC 等条件支付的基础 |
| **多签组合** | 例如 P2WSH 中的 `2 <公钥A> <公钥B> <公钥C> 3 OP_CHECKMULTISIG` | `witness: <空占位> <签名A> <签名B> <WitnessScript>` | 取决于外层类型 | 常见于 2-of-3 多签钱包、闪电网络 |

## 疑问及解答

1. 什么是脚本？

   答：以纯文本形式保存、由解释器逐行直接执行的指令集合‌，核心作用是自动化完成特定任务或控制其他程序的行为。
   
2. 什么是脚本执行堆栈？

   答：比特币的脚本语言被称为基于栈的语言，它使用了一种名为栈的数据结构。栈是一种非常简单的数据结构，可以形象地理解为一叠卡片。栈有两个基本操作：入栈（push）和出栈（pop）。入栈操作将元素添加到栈顶，出栈操作则从栈顶移除元素。

3. 为什么nLockTime（锁定时间）与 OP_CLTV (检查锁定时间验证) 必须结合使用？

   答：nLockTime 锁的是“交易打包的时间”，而 OP_CLTV 锁的是“特定UTXO被花费的条件”。

4. IP9软分叉激活隔离见证是如何实现新旧节点完全兼容？

   答：隔离见证后交易输出变成了 OP_0 <20字节公钥哈希>。旧节点在验证花费交易时，全程只处理自己能识别的部分：它读取交易输入的scriptSig字段，发现P2WPKH的scriptSig是空的，直接把空值压入栈。接着执行锁定脚本OP_0 <20字节公钥哈希>，最终栈顶留下非零值，旧节点直接判定脚本执行通过，交易合法。整个过程里，旧节点根本不会去读取、解析后面的见证字段，自然完全感知不到签名和公钥的存在，也不会因为见证数据的存在报错。所以对旧节点而言，这是一笔任何人都可以花费的UTXO。

5. ‌什么是交易延展性漏洞？隔离见证如何解决这个问题的？
   
   答：交易延展性漏洞‌是比特币早期的一个经典底层漏洞：第三方可以在不破坏交易签名有效性、不改变交易核心支付信息的前提下，修改签名里的部分可变字节，最终让这笔交易的TXID（交易哈希）发生变化。而这笔修改后的交易依然能被节点判定为合法，正常广播到网络中。隔离见证把签名、公钥等见证数据从交易主体里剥离，放到独立的witness字段中，计算TXID时完全不包含见证数据。哪怕攻击者篡改签名，也不会影响TXID的最终结果，从根源上彻底消除了这个漏洞，这也是闪电网络等二层协议能安全落地的核心前提。

## 本章节评价
通过本章的学习，了解到了比特币在交易过程中有2个非常重要的动作——交易输出和交易输入。交易输出是把比特币锁定在“一个房间”，定义解锁规则；而交易输入则是打开“这个房间”并花费里面的比特币，提供对应的解锁证明。而实现这个过程的技术也在不断升级和更新，从最初的P2PKH，到P2SH，到多种支付条件和逻辑的实现，再到隔离见证的结构化升级，彻底解决了交易延展性漏洞，后续依托隔离见证的脚本版本化能力，MAST被正式引入，实现了多签方式的隐私化更新，再到最近的Taproot升级等，为实现比特币多样化的支付场景，提升安全性和隐私性提供了可能。
